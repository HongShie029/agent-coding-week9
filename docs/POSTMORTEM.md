## 요약 (3줄)
- 14:10 에 배포된 api v1.4.0(DEP-1042)에서 환경 변수 `DB_POOL_SIZE` 가 20 에서 5 로 줄어, 14:16 부터 DB 커넥션 풀이 고갈되었다.
- 주문 목록 조회와 주문 생성이 연결 대기 타임아웃으로 실패해 오류율과 응답 시간(p95)이 급등했다.
- 같은 배포에 변경 3건(주문 필터 개선 · 환경 변수 정리 · lodash 패치)이 묶여 있었고, 원인은 그중 환경 변수 정리이다.

## 영향
- 시작 시각 / 감지 시각 / 복구 시각: 14:16 / 14:22 (알림 `error-sustained`, 첫 이상 후 6분) / 번들 범위(15:29)까지 복구 기록 없음
- 영향 범위(요청 · 주문 · 결제):

  - 지연: p95 가 평소 400ms대에서 1,300ms대로 상승
  - 주문 · 결제: `GET /orders`, `POST /orders` 가 타임아웃으로 실패해 주문 내역 조회와 결제 후 주문 확인에 문제가 생겼다(고객센터 접수 내용).

## 근본 원인과 기여 요인
- 근본 원인: 용량과 직결된 설정(`DB_POOL_SIZE`)을 20 에서 5 로 줄였고, 그 영향을 확인하지 못한 채 운영에 반영되었다.
- 왜 배포 전에 못 막았나(게이트): 설정 변경을 "환경 변수 정리"라는 정리 작업으로 취급해, 용량 영향(커넥션 수 대비 동시 요청)을 확인하는 검증이 없었다. 계약서의 게이트 규칙표에도 설정 변경의 용량 영향을 검증하는 규칙이 없다.
- 왜 늦게 알았나(알림): 첫 이상(14:16)보다 6분 뒤인 14:22 에 오류율 알림이 울렸다. 오류율 알림이 "4분 연속" 조건이라 지속성을 확인하는 동안 시간이 걸렸고, 풀 고갈 자체를 직접 보는 알림은 없었다.
- 왜 오래 걸렸나(런북 · 롤백): 한 배포에 변경 3건이 묶여 있어 어느 변경이 원인인지 가려내야 했다. 번들 범위 안에서는 롤백이나 설정 복구 기록이 확인되지 않는다.

## AI 도구를 어떻게 썼나
- 에이전트에게 무엇을 시켰고, 어떤 결론이 나왔나: 번들(접수 내용 · 알림 · 배포 기록 · 지표 · 로그)을 주고 원인 · 최초 이상 시각 · 근거 로그 ID 를 분석시켰다. 결론은 "DEP-1042 안의 `DB_POOL_SIZE 20 → 5` 가 원인, 최초 이상 14:16, 근거 L0051 · L0056 · L0057" 이었다.
- 사람이 확인한 방법(로그 ID 대조): 터미널에서 `incidents/INC-1/logs.jsonl` 로 근거 ID 3개가 실제로 존재하는지, 내용이 원인(풀 크기 변경 · 풀 고갈 · 타임아웃)을 보여 주는지, 시각이 인과(배포 14:10 → 오류 14:16)에 맞는지 출력해 확인했다.
- AI 가 틀렸거나 미끼에 속은 부분: 이번 분석에서 AI 가 미끼에 속은 사례는 없었다. 같은 시각대에 있었으나 원인이 아니어서 근거에서 제외한 로그는 캐시 미스 경고(L0006 · L0027)와 폐기 예정 경고(L0044 · L0075)이다. 접수 내용(14:20)과 알림(14:22) 시각은 감지 시각일 뿐 최초 이상 시각이 아니므로 쓰지 않았다.
